# LinkedIn 經營起手式

> LinkedIn 跟其他社群最大的差別是：**它是搜尋驅動，不是動態驅動**。
> 別人不是滑到你，是「搜」到你。這一點會改變你所有的經營順序。

---

## 一、先修檔案，再想內容

新手最常見的順序錯誤是：一開始就想「我要發什麼」。

但在 LinkedIn 上，發文的觸及取決於你的人脈規模，而**檔案（Profile）決定了你會不會出現在別人的搜尋結果裡**。檔案沒修好就開始發文，等於在一個沒人找得到的房間裡講話。

下面是按「投報率」排序的檔案優化清單——**排前面的花五分鐘、影響最大**：

### 1. 求職意向的目標職稱（Open to Work）

這是最多人設錯、也最痛的一項。

如果你的目標職稱寫的是自我期許型的頭銜（例如「系統架構師」「創意總監」），但招募者實際在搜尋框打的是「iOS Engineer」「Android Developer」，**你們永遠不會相遇**。

> [!tip] 用招募者的詞，不是你的詞
> 去看幾則你真的想要的職缺，把它們標題上的字，原樣填進去。同一個職務常有多種寫法（iOS Engineer / iOS Developer / Mobile Application Developer），全部都填。

五分鐘、零成本、影響最大。

### 2. Headline（標題列）

搜尋權重最高的欄位。

不要只放「某某公司 工程師」這種光禿禿的職稱，**塞進你的技術/專業關鍵字**：

```
❌ 軟體工程師 at 某某公司
✅ iOS Engineer｜Swift · SwiftUI · Kotlin · AWS IoT · MQTT
```

### 3. 技能（Skills）

職缺匹配演算法會吃這個欄位。

- 把技能數量補到 25～30 個（很多人只填十來個）
- **最重要的技能排最前面**
- 把技能**綁定到對應的工作經歷**（LinkedIn 支援這個關聯，會增加可信度）

### 4. 經歷描述

很多人的經歷只有「職稱＋起訖時間」，沒有內容。

> [!warning] 不要靠回憶或推測補
> 拿你的正式履歷（104、CakeResume、PDF 履歷都行）當**校對來源**，逐段核對後再填。年份、專案名稱、負責範圍寫錯，是招募者面試時第一個會抓到的東西。

### 5. 其他基本項

About（自我介紹）、學歷、**真人大頭照**、自訂網址（`linkedin.com/in/你的名字`）。

## 二、用 AI 協作的正確分工

這幾項改起來很瑣碎，很適合跟 AI 分工：

- **AI 負責**：盤點缺口（對照目標職缺，告訴你哪裡不夠）、擬第一版文字
- **你負責**：逐項貼上、用真實履歷校正事實

不要期待自動化。LinkedIn 的 **Profile 編輯 API 不開放給一般開發者**，所以「一鍵更新檔案」這條路本來就走不通，人工貼上反而是唯一解，也順便強迫你看過每一個字。

---

## 三、冷啟動：聯絡人只有十幾個怎麼辦

這是最容易讓人放棄的階段——**發文幾乎零觸及**，因為 LinkedIn 的動態主要推給你的一度人脈。

關鍵認知：**「擴人脈」和「發文」必須並行，不能先做完一個再做另一個。**

每天花的力氣可以這樣配：

- **5～10 個附註邀請**。純按「建立關係」通過率低，加一句「看到你在做 XX，我最近也在弄類似的東西」差很多
- **10 分鐘在別人的專業貼文下留有料的留言**。這是冷啟動期最被低估的動作——**留言的觸及不受你自己同溫層大小限制**，你是在別人的場子裡被他的讀者看到

## 四、內容配比與節奏

不要每篇都在講同一件事，也不要每篇都在求職。一個可用的四支柱配比：

| 支柱           | 比例 | 內容                         |
| -------------- | ---- | ---------------------------- |
| 專業實戰       | 40%  | 你本行的具體案例、踩坑、解法 |
| 工作流程與工具 | 25%  | 你怎麼做事、用什麼工具       |
| 興趣延伸       | 15%  | 側寫你這個人，不是只有職稱   |
| 職涯敘事       | 20%  | 轉折、選擇、為什麼走到這裡   |

**節奏**：每週 1～2 篇，上班日早上發。

同一篇貼文的主要曝光窗大約是 **24～48 小時**，所以新的一篇至少隔幾天再發，不然是自己稀釋自己。

## 五、舊文怎麼轉成貼文

如果你以前寫過部落格、技術文章，那是現成的素材庫。但**不能用「我寫了一篇新文章」的口吻直接貼連結**——三年前的文章這樣發，只會顯得你在清庫存。

### 正確角度：把舊文放進個人敘事

同一篇三年前的教學文，換個框架就完全不一樣：

```
❌ 我三年前寫過一篇關於 XX 的教學，分享給大家
✅ 這是我從 A 領域走進 B 領域的起點
```

然後挑文章裡**最有記憶點的具體素材**當開場鉤子。抽象的「我學到很多」沒有人有感，具體的除錯故事才有——例如「一個陣列越界不但沒有 crash，還安靜地吐出一堆亂碼」，同行看到會心一笑，因為他們也踩過。

結尾再連回你現在在做的事。**舊文是素材，不是主角。**

### 同主題的續作：換「技術選型」的角度

如果你有系列文（例如先寫了 A 做法、後寫了 B 做法），第二篇不要再發一次教學。改成講**同一件事、兩種做法的取捨**：什麼情境選 A、什麼情境選 B、真實產品裡你選了哪個。

這比「又一篇教學」高一個層次——展示的是**判斷力**，不是知識量。

### 系列上下集要合併成一篇發

拆開發只會稀釋。

### 貼文開頭不要綁時間

寫「前一篇文章裡」而不是「上週」。這樣草稿寫好後，什麼時候發都行，發文時機就有彈性了。

## 六、寫作風格

- 用**敘事段落**，口語平順
- 避免「條列＋金句」那種一眼就看得出來的 AI 腔
- 內容裡不用特別提你用了哪個 AI 工具

---

## 七、自動化的紅線

LinkedIn 對自動化行為的偵測很嚴，以下這些是**帳號風險**，不論工具講得多安全都不要碰：

| ❌ 不要做                | 說明                                                 |
| ------------------------ | ---------------------------------------------------- |
| 自動投遞職缺、爬取職缺   | 違反使用條款                                         |
| 自動私訊                 | 最容易被判定為濫用                                   |
| 自動按讚、自動追蹤等互動 | 同上                                                 |
| 任何瀏覽器自動化         | Playwright、Selenium、帶 Cookie 模擬登入，一律高風險 |

> [!note] 那什麼可以做？
> 官方 API 有開放**發布貼文**（`w_member_social`）。也就是說「先產草稿 → 人工看過 → 一鍵發布」這條管線是合規的。
> 但要注意 token 大約 **60 天就會過期，而且一般開發者拿不到自動續期的權限**——所以真正的無人值守排程器做不出來，每兩個月要手動重新授權一次。設計流程時要先接受這件事。
